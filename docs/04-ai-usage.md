# 04 AI 使用说明与个人贡献

## 我的角色与参与方式

本项目采用人机协作方式完成。我主要参与选题与需求输入、技术方案确认、真实模型选择与环境配置、问题修复方向确认，以及交付前的复核组织；AI 辅助完成方案细化、代码编写、测试执行和文档整理。

我的参与贯穿“选题 → 方案确认 → 真实模型验证 → 问题反馈与修复 → 交付复核”。其中，选择哪道题、采用什么实现路线、使用哪个模型，以及何时发起进一步检查，均有我的参与。代码与测试的具体实现由 AI 辅助完成，以下按阶段说明各自承担的工作。

## 我的具体参与与项目中的体现

| 阶段 | 我的参与 | 项目中的体现 |
|---|---|---|
| 需求输入与选题 | 提供四道题的完整题面，结合 AI 对验收点、风险和工作量的比较，最终选择第 1 题 | 将交付聚焦于素材审核、冲突处理、用户确认和草稿保存，围绕六项必须验收点组织实现 |
| 技术路线确认 | 确认采用原生实现和 OpenAI 兼容接口的方案 | 使用 Python 工具循环和明确的业务护栏；保留离线 Mock 与真实模型两种运行入口 |
| 模型选择与配置 | 选择 DeepSeek 作为真实验证模型，并提供、配置本地 API key | 除离线流程测试外，形成 `examples/llm/` 中的真实模型运行记录 |
| 修复方向确认 | 对第一轮真实模型运行暴露的问题，确认修复方向，由 AI 定位、修改并执行回归验证 | 修复幂等判定、缺失请求信息处理和结束校验等问题，过程见 [评估文档](03-evaluation.md) |
| 交付前复核 | 主动要求 Codex 对照笔试题面检查仓库；修改后再次发起复核 | 在已有测试之外发现保存失败结论矛盾、真实写盘异常和非法时段三个缺口；修复版本通过 29 个测试及 12 个 Mock 场景复跑 |
| 文档完善 | 提出丰富文档、进一步说明个人参与的要求 | 补充输入输出契约、设计取舍、证据边界和复核说明，使评审能够对应需求、代码与运行结果 |
| 交付管理 | 确认初始提交与推送；后续通过对话推动审查、修复后的检查和文档更新 | 将代码、测试、输入输出、运行记录与说明集中在同一 GitHub 仓库 |

上述个人参与中的选题、方案确认、模型配置和第一轮修复确认沿用项目原有协作记录；发起 Codex 审查、修改后复核和文档完善体现在后续交付过程。测试结果来自 AI 执行与工具输出，个人贡献主要体现在方向选择、协作推进和交付要求的提出。

### Claude Code：方案细化与工程实现

使用工具：Claude Code，模型为 Claude Opus 5.5，在 Claude 桌面 App 中使用。

| AI 辅助内容 | 具体范围 |
|---|---|
| 选题分析 | 比较四道题的验收点、风险、工作量和业务贴合度，提供选题建议 |
| 方案设计 | 细化工具职责、save_draft / finish 护栏、幂等键和事实字段生成方式 |
| 编码与数据 | 编写 `src/`、`scripts/record_examples.py` 及合成素材、规则与排期 |
| 测试与调试 | 编写测试、执行 Mock 和真实模型场景，分析偏差并修改代码 |

方案细节、编码、调试和测试执行均包含 AI 工作。我的选题、方案确认和修复方向确认，与 AI 的具体实现分别列示。

Codex 审查与文档补充没有重新调用 DeepSeek，也没有增加新的真实模型实验结果。此前修复提交中的代码与本次文档修改分别保留在 Git 历史中。

## 验证方式与结果边界

- **离线自动化验证**：`python -m pytest -q`，修复版本复核结果为 29 passed，覆盖六项必须验收点及已定义的护栏场景。
- **Mock 场景复跑**：`examples/mock/` 共 12 个场景，验证流程、工具协议、幂等、故障处理和状态输出。
- **真实模型记录**：DeepSeek `deepseek-chat` 完成两轮运行，第一轮暴露四个偏差，第二轮形成 12 场景记录；第三轮修复后，重新录制了受影响的场景。详见 [评估文档](03-evaluation.md)。

我通过发起复核推动交付问题被发现和检查；测试、运行及问题定位由 AI 辅助执行。当前真实模型记录属于有限样例，尚未统计重复运行成功率，也没有生产环境效果数据。文档改写不会增加个人独立编码、人工逐项测试或已验证业务收益的主张。

## 数据与凭据处理

运行数据均为合成资料，不包含真实素材、版权凭证或业务排期。真实模型模式会将请求和工具返回发送至配置的模型接口，接入真实业务前应审查发送字段。真实密钥保存在本地环境配置中；仓库仅提供 `.env.example` 占位配置。
