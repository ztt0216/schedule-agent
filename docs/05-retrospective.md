# 05 复盘

| AI 生成代码、测试、文档并跑通 Mock | 约 15 分钟 |
| 两轮 DeepSeek 运行、修复与文档更新 | 约 20 分钟 |

## 最难的问题

**如何让模型来决策，同时又保证不越权、不虚报。**

- 如果把所有判断都写成 if-else，就不满足题目对 ReAct 的要求。
- 如果把所有判断都交给模型，"擅自确认""声称已保存"这类关键缺陷就只能靠 prompt 去约束，没有保证。

最后的做法是把系统拆成三层：

1. **模型选动作**：下一步做什么、选哪个替代时段、何时结束。
2. **代码校验约束**：拒绝不合规的动作，把原因作为观察结果回传给模型，让模型自己修正。
3. **代码生成事实字段**：保存状态、是否发布这类字段，只看实际执行结果，不看模型怎么说。

## 学习收获

- **护栏应该以"可观察的拒绝"的方式回到循环里，而不是直接抛异常。** 这样模型有机会自我修正，trace 里也能看到修正过程。
- **幂等键的选取决定了"重复"的语义。** 键里不放 `confirmations`，用户确认后的第二轮才会更新同一份草稿，而不是新建一份。
- **离线 Mock 只能读消息历史。** 它和真实模型处在同一个信息边界上，Mock 结果才适合作为协议与流程的验证证据；它仍不能替代真实模型实验。
- **真实模型是测试护栏的最好工具。** 第一轮 DeepSeek 运行暴露了两个 Mock 测不出来的 bug：保存失败后护栏误报"已写入"、JSON 解析失败后报错信息不准确。护栏的报错本身也是给模型的"观察"，必须准确且可执行。

- **"事实只认存储层"要贯彻到每一层。** 第三轮评审发现，报告顶层的保存状态是对的，但单个素材的结论和存储内部的内存状态仍然可能"虚报"。护栏和存储都必须以实际写入为准。

## 下一步

1. 每个场景用真实模型重复跑 N 次，统计决策一致率（temperature=0 也不能保证完全稳定），并对比其他模型。
2. 失败步骤续跑：把执行器的 facts 落盘，下次运行时从断点恢复，不再重复读取和检查。
3. 支持跨日期改期：替代时段扩展到相邻日期，但仍然必须走确认流程。
4. 给草稿存储加文件锁，或换成 SQLite 并加唯一约束，解决并发写入的问题。

## 从问题到工程改进

这次迭代最有价值的反馈来自“正常流程之外”的错误：第一轮真实模型暴露了 prompt 与错误反馈的问题，第三轮代码审查又暴露了已通过测试的保存逻辑仍有盲点。两类检查关注点不同，不能用一套 Mock 策略的通过结果代替全部验证。

保存失败的问题贯穿三个层次：存储层不能先改内存再假定落盘成功；执行层要把真实文件系统异常转换为工具观察；报告层不能从“尝试保存过”推导出“已经排期”。只修复其中一层，其他层仍可能产生相反结论。因此，回归测试需要同时检查工具返回、文件/内存状态和最终报告，而不只是搜索 summary 中是否出现“失败”。

另一个取舍是保留建议而不夸大完成度。存储失败不代表模型没有产生有用建议，但建议也不能被当成排期结果。unsaved_suggestion 保留可供人参考的信息，suggested_slot 则仅表示保存成功的草稿内容；两个字段使用户能继续处理，同时清楚知道当前还差哪一步。

## 下一步的优先顺序与验收方式

| 优先级 | 计划 | 完成时应提供的证据 |
|---|---|---|
| 1 | 将时段确认和风险审批拆开，并校验请求及工具参数类型 | 只确认时间时，商业风险仍待审批；畸形输入返回明确错误 |
| 2 | 重复真实模型评估，保留失败样例 | 固定场景的多次运行统计、工具调用量及失败分类 |
| 3 | 统一草稿占用管理并处理并发 | 两个请求争用同一时段时，不会各自生成互相冲突的有效安排 |
| 4 | 增加断点恢复与更完整的时段搜索 | 故障恢复后不重复已完成的副作用；有限候选不足时不会误报全天无解 |

这些都是未来工作，不属于当前交付成果。当前项目的价值是一个可运行、可观察、能够解释边界的原型；线上审批、真实平台发布、完整内容审核和生产效果均未验证。
