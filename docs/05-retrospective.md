## 最难的问题

**如何让模型来决策，同时又保证不越权、不虚报。**

- 如果把所有判断都写成 if-else，就不满足题目对 ReAct 的要求。
- 如果把所有判断都交给模型，"擅自确认""声称已保存"这类关键缺陷就只能靠 prompt 去约束，没有保证。

最后的做法是把系统拆成三层：

1. **模型选动作**：下一步做什么、选哪个替代时段、何时结束。
2. **代码校验约束**：拒绝不合规的动作，把原因作为观察结果回传给模型，让模型自己修正。
3. **代码生成事实字段**：保存状态、是否发布这类字段，只看实际执行结果，不看模型怎么说。

## 学习收获

- **护栏应该以"可观察的拒绝"的方式回到循环里，而不是直接抛异常。** 这样模型有机会自我修正，trace 里也能看到修正过程。
- **幂等键的选取决定了"重复"的语义。** 键里不放 `confirmations`，用户确认后的第二轮才会更新同一份草稿，而不是新建一份。
- **离线 Mock 只能读消息历史。** 它和真实模型处在同一个信息边界上，Mock 跑通的流程对真实模型才有参考意义。
- **真实模型是测试护栏的最好工具。** 第一轮 DeepSeek 运行暴露了两个 Mock 测不出来的 bug：保存失败后护栏误报"已写入"、JSON 解析失败后报错信息不准确。护栏的报错本身也是给模型的"观察"，必须准确且可执行。

- **"事实只认存储层"要贯彻到每一层。** 第三轮评审发现，报告顶层的保存状态是对的，但单个素材的结论和存储内部的内存状态仍然可能"虚报"。护栏和存储都必须以实际写入为准。

## 下一步

1. 每个场景用真实模型重复跑 N 次，统计决策一致率（temperature=0 也不能保证完全稳定），并对比其他模型。
2. 失败步骤续跑：把执行器的 facts 落盘，下次运行时从断点恢复，不再重复读取和检查。
3. 支持跨日期改期：替代时段扩展到相邻日期，但仍然必须走确认流程。
4. 给草稿存储加文件锁，或换成 SQLite 并加唯一约束，解决并发写入的问题。
