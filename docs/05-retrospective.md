# 05 项目复盘：从流程跑通到结果可信

## 投入与当前交付

初始实现的原有用时估计如下，分项相加约 65 分钟。该估计不是计时工具记录，不包含后续 Codex 审查、第三轮修复和文档补充，因此不能代表最终交付的全部投入。

| 阶段 | 原有用时估计 |
|---|---|
| 读题与选题讨论 | 约 30 分钟 |
| AI 生成代码、测试、文档并跑通 Mock | 约 15 分钟 |
| 两轮 DeepSeek 运行、修复与文档更新 | 约 20 分钟 |

当前交付包含工具调用循环、保存与结束护栏、本地幂等草稿、29 个自动化测试，以及 Mock 和 DeepSeek 的场景记录。多次真实模型实验、独立风险审批、跨草稿占用协调和失败步骤续跑尚未完成。个人与 AI 的具体分工见 [AI 使用说明](04-ai-usage.md)，本篇围绕项目中实际出现的问题分析设计与验证方法。

## 1. 最难的不是选出一个时间，而是明确系统凭什么宣布完成

题目的表面任务是审核与排期，但一个可用时段背后至少有四个独立问题：素材是否完整、规则是否允许、用户是否同意变更，以及草稿是否真正保存。它们不能相互替代：时间空闲不能证明版权有效，用户同意改期不能证明商务风险已获审批，模型生成了合理建议也不能证明建议已经落盘。

因此，任务状态更适合被看成一组事实，而非一个“成功/失败”布尔值：审核状态、确认状态、存储结果、执行是否结束需要分别表达。当前实现用 review_status、decision、draft.status 和 task_status 做了初步区分。全部素材被有依据地阻断时，审核处理可以 completed，但不能说全部排期成功；相反，保存成功后达到步数上限，任务仍可能 incomplete，而已写入的草稿不会自动消失。

这改变了我对交付结果的判断：应先定义“可以向用户承诺什么”，再决定需要哪些工具和字段。工具调用数量或模型回答流畅程度，都不能代替对完成条件的定义。

## 2. 保存失败暴露的是状态证据断裂，单独修补一句提示词不够

保存问题在不同轮次反复出现，根因是“准备做”“尝试过”“已成功”在代码不同位置被混用。第一次修复允许模型在保存失败后如实返回 unresolved，但结束校验的另一条分支仍接受“尝试保存过的条目”作为 scheduled 的依据；顶层状态正确，单项结论却可以相反。

第三轮审查进一步发现，存储层先更新内存、再写文件。真实写盘失败后，下一次重试可能在内存里找到相同内容，直接返回 duplicate。此时去重逻辑本身按预期执行，却建立在错误的前提上：内存中的记录被当成了已经持久化的记录。

| 层次 | 原来的错误假设 | 修复后的约束 |
|---|---|---|
| 存储层 | 内存中已有相同内容，就可以判定重复保存 | 文件写入与替换成功后才更新内存 |
| 工具层 | 故障注入返回失败，就足以覆盖保存失败 | 捕获真实 OSError，将其转成 storage_error 观察 |
| 结束校验 | 存在尝试保存的条目，就能接受排期结论 | scheduled / pending_confirmation 只能依据存储成功的条目 |
| 报告层 | 保存失败时仍可把建议放在排期结果字段 | 未保存建议放入 unsaved_suggestion，suggested_slot 保持为空 |

由此得到一个具体的校验原则：**排期成功结论必须能追溯到成功保存的匹配条目。** 这条约束需要跨模块成立，不能只检查某个函数返回 ok，或报告中是否出现了“失败”二字。对应回归测试应同时检查结论、保存状态、建议字段和实际写入情况。

这里还有一个未来接入远程工具时需要重新设计的问题：请求超时不一定代表服务端未写入。当前本地存储和故障注入不构成对“远端写入成功但响应丢失”的验证。若改为远程保存，应支持按幂等键查询结果或返回“结果待核实”，再决定是否重试，不能直接套用本地失败语义。

## 3. 护栏返回的错误也是模型的输入，反馈错误会制造新的错误

第一轮真实模型运行中，模型在保存失败后给出 unresolved，护栏却反馈“已写入草稿”，这会引导模型放弃原本正确的结论。另一个问题是工具参数 JSON 不合法，却收到“缺少素材结论”的反馈；模型重复提交类似错误，实际需要修复的却是参数格式。

这说明护栏除了拒绝不合规动作，还承担了诊断接口的职责。有效反馈至少应回答三个问题：发生了哪类错误、这次是否产生副作用、下一步允许做什么。例如 storage_error 表示本次写入失败；finish_rejected 应明确指出“保存失败，不能给出 scheduled，请报告 unresolved”，而不是笼统要求重试。

目前通过 invalid_json、validation_failed、storage_error 等错误类别改善了这一点，但错误处理尚未形成完整协议：任意类型错误、最终模型网络异常和端到端超时仍有缺口。下一步需要按错误类别定义恢复动作，而不是把所有异常都交给模型自由重试。不可重试的参数或权限问题应请求修正；可能恢复的工具故障才适合有限重试。

## 4. 测试全部通过，仍可能遗漏实现与测试共同相信的假设

Mock 策略是一个知道“正确流程”的确定性执行者，它倾向于在保存失败后主动选择 unresolved，也会按预期先查询再保存。因此，即使结束护栏能够错误接受 scheduled，或保存工具接受非法时间，Mock 也可能从不触发这些分支。

项目的实现、Mock 和测试都包含 AI 辅助工作，存在共享设计假设的风险。增加同一条正常路径的样例数量，未必能发现这种盲点。第三轮审查采用了不同的检查方式：让模型式调用故意跳过查询、在失败后提交成功结论，并用真实文件路径错误替代预设故障码，从而检查约束是否由系统自身保证。

| 验证方式 | 主要价值 | 本项目中的例子 |
|---|---|---|
| 正常与业务异常场景 | 检查核心链路及输出符合业务预期 | 正常排期、缺信息、规则风险和时段冲突 |
| 故意错误的模型动作 | 检查系统能否拒绝不应接受的调用 | 未经确认改期、保存失败后声称 scheduled、非法时段 |
| 替换底层真实条件 | 检查抽象接口之外的失败 | 存储路径不可写、占用时段被解除 |
| 相同请求的对照运行 | 检查动作是否随观察变化 | 05a 与 05c 使用相同请求、更换占用数据 |

29 个测试通过是对已有断言的证据，不是对所有输入的保证；12 组真实模型记录展示了有限运行中的决策，也不是稳定成功率。后续应将“业务处理完成率”和“错误成功声明率”分别统计。对于本题，明确报告无法完成通常比没有依据地宣布完成更可接受，因此不能只优化表面的成功数量。

## 5. 幂等性与确认机制，本质上都是业务语义的选择

请求键不包含 confirmations，使“用户接受建议后的第二轮”能够更新同一份草稿。内容哈希不包含 note，使模型措辞改变不会导致无意义的版本递增。这两个决定都在回答一个业务问题：哪些变化仍然属于同一项工作，哪些变化应形成新的交付？

当前选择适合演示，但有明确代价：修改原始时间会产生新请求；同一素材的多次发布没有独立任务身份；不同草稿也不共享占用预留。若继续扩展，宜引入稳定的请求 ID、明确的版本和草稿生命周期，而不是不断向哈希规则增加例外。并发控制还应保证跨请求的冲突检查和占用写入一起生效，单独给 JSON 文件加锁只能解决其中一部分问题。

确认机制也有相似的简化。当前 confirmations 仅表达“素材 ID → 时段”，无法独立表示商务风险审批，也没有证明确认人的身份。时间确认与风险审批应有各自的对象和依据；否则，一次接受 19:00 的操作可能被错误扩大为对全部风险的同意。这个边界应在增加真实业务能力之前解决。

## 6. AI 协作中的学习：把“检查完成”改成可核对的问题

我的参与包括选题、路线确认、模型选择、修复方向确认，以及主动发起交付检查。实际的方案细化、编码、运行与问题定位由 AI 辅助完成。此次审查让我看到，仅询问“是否符合要求”还不足以形成完整的验收方法，需要把要求拆成可被反例挑战的判断。

例如，对“保存失败必须明确返回失败”，应追问：预设故障码以外的文件异常会怎样？失败后再次保存会不会被误判重复？模型忽略失败、直接说成功时，系统能否拒绝？同一个业务要求通过这些问题被落实为不同层次的检查，而不只是 README 中的一条完成声明。

如果重新组织这次工作，我会更早要求 AI 列出状态定义和必须保持的约束，再编写对这些约束的反例测试；真实模型出现偏差时，先区分模型决策、工具反馈和状态实现的问题，再选择修改提示词或代码。这样做的价值是让每次修复都有可解释的原因和可复核的证据，避免只让当前样例重新跑通。

## 7. 下一步优先级：先缩小错误承诺的空间，再扩展功能

| 优先级 | 改进 | 验收方式 |
|---|---|---|
| 1 | 独立表达时段确认与风险审批；增加输入及工具参数校验 | 仅确认时间时，商务风险保持待审批；畸形参数返回明确错误 |
| 2 | 统一错误与结果语义，覆盖模型网络失败和状态不一致 | 不会因工具/网络异常直接丢失已有执行信息；保存失败与单项结论一致 |
| 3 | 固定场景重复运行真实模型，并保留全部失败 | 分别统计业务状态正确率、错误成功声明、重试恢复、调用数、耗时和费用 |
| 4 | 建立跨草稿占用协调与并发控制 | 两个请求竞争同一时段时，不会分别生成冲突的有效安排 |
| 5 | 扩展候选搜索，再考虑断点恢复 | 三个候选不足时不会直接认定全天无解；续跑会重新检查可能过期的规则与占用事实 |

断点恢复尤其不能只把 facts 落盘后直接复用：素材、授权或排期可能在暂停期间变化。恢复流程必须区分可重用的执行记录和需要刷新验证的业务事实，否则“少调用一次工具”可能换来基于过期信息的安排。

以上均为后续计划。当前项目证明了核心流程可以运行、部分错误能被观测和拒绝，并有可追溯的修复过程；尚未证明完整内容审核、生产可靠性或实际运营收益。下一轮迭代应继续围绕完成条件和证据质量推进，再判断是否需要框架、更复杂的编排或更多工具。
