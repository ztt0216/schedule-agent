# 02 方案

## 调用流程

```
请求 ──► LLM 选择动作（tool call + reason）
          │
          ▼
     执行器 ToolExecutor ── 故障注入 / 护栏校验 ──► 观察结果（JSON）
          │                                       │
          └────────── 写回消息历史 ◄──────────────┘
          │
   重复以上过程，直到 finish 被护栏接受，或达到 max_steps
          │
          ▼
   build_report：事实字段（草稿状态、published、审核状态）由代码根据执行记录生成
```

工具共 6 个：

| 工具 | 作用 |
|---|---|
| `read_material` | 读取素材元数据，返回缺失的必填字段 |
| `check_rules` | 按规则检查，返回风险等级 block / verify / confirm |
| `verify_license` | 补查授权状态 |
| `query_slots` | 查询时段是否可用，返回同日最近的 3 个替代时段 |
| `save_draft` | 保存草稿 |
| `finish` | 提交每个素材的结论 |

**工具集中没有发布能力**，从结构上排除了越权发布。

## 动态决策点

| 观察到的结果 | 模型的下一步 |
|---|---|
| `missing_fields` 非空，或素材不存在 | 停止处理该素材 → `need_info` |
| 风险 `block` | 阻断 |
| 风险 `verify` | **补查** `verify_license`：expired → 阻断；verified → 继续 |
| 风险 `confirm` | 原时段可用也只能标记待确认 |
| 时段被占用 | 从替代时段中选一个，避开同批其他素材指定的时段 → **请求确认** |
| 请求里带 `confirmations` | 直接查询已确认的时段，可用则标记 confirmed |
| `tool_unavailable` / `storage_unavailable` / `storage_error` | 重试一次；仍失败则标记 `unresolved` 或如实报告保存失败 |
| 护栏返回 `validation_failed` / `finish_rejected` | 按 violations 修正后重新提交 |

**两条代表性路径**，同一个素材 M01、同一个请求、只换已有排期：
- 18:00 被占用：`query_slots` → 选择替代时段（多素材场景为 20:00）→ `pending_confirmation`。
- 18:00 空闲：`query_slots` → 原时段 → `confirmed`。

见 `examples/mock/05a_submit` 与 `05c_resubmit_after_slot_freed`。

## 模型与代码的分工（核心取舍）

题目规定"仅有固定条件分支不算 ReAct"，同时又要求"不得越权、不得虚报"。我的做法是：

- **模型决定动作**：调用顺序、是否补查、选哪个替代时段、何时请求确认或结束，全部由模型根据观察结果决定，代码里没有固定的执行顺序。
- **代码只做约束校验，不替模型做决定**：
  - `save_draft` 护栏会拒绝以下情况，并把原因作为观察结果返回给模型：
    - 素材没读过或没做规则检查
    - 有阻断风险
    - 授权没补查
    - 改了渠道或日期
    - 时段已被占用，或同一草稿内重复
    - 未经确认就标记 confirmed
  - `finish` 护栏会拒绝以下情况：
    - 结论与草稿不一致
    - 没有依据的阻断
    - 遗漏素材
- **事实字段不交给模型**：`draft.status` 来自存储层的返回值，`published` 恒为 false，`review_status` 来自执行器记录的观察。即使模型声称"已保存"，报告也不会采信。

`tests/test_guardrails.py::test_loop_feeds_violation_back_and_model_corrects` 演示了这个闭环：模型先越权确认、再虚报 scheduled，两次都被拒，之后修正为 pending_confirmation。

## 幂等与确认边界

- **幂等键**：`draft_id = hash(素材, 渠道, 日期, 时间)`，不包含 `confirmations`。
  - 内容相同时重复保存 → `duplicate`，不写入。
  - 第二轮确认或排期变化后内容不同 → 同一个 `draft_id` 的版本号 +1。
  - 因此"相同请求只有一份草稿"。
- **确认边界**：`confirmed` 只能出现在两种情况：
  - 用户原始时段，且没有 confirm 级风险；
  - `confirmations` 中用户明确确认过的时段。

## 技术取舍

| 选择 | 理由 |
|---|---|
| 原生实现，不用框架 | 循环核心约 60 行。护栏要插在"工具执行前"和"结束前"两个位置，自己写比在框架回调里改更直接，也方便评审逐行核对 |
| 只依赖标准库，用 urllib 调用 OpenAI 兼容接口 | 离线即可运行测试；切换 DeepSeek、千问、OpenAI 只需改 `.env` |
| 每个工具带 `reason` 参数 | 满足"简要决策依据"，同时不需要提交模型内部的思维过程 |
| MockLLM 只读消息历史 | 和真实模型的信息边界一致，不偷看执行器状态，可以验证消息与工具协议能走通，真实模型效果仍需单独运行验证 |
| 步数上限按工具调用计（含 finish 和被拒的调用） | 防止模型在护栏拒绝和重试之间无限循环 |
| 规则命中、时段计算用确定性代码 | 这些是事实查询，交给模型反而会引入不确定性 |

## 模块职责与数据流

| 模块 | 主要职责 | 关键边界 |
|---|---|---|
| `cli.py` | 读取请求、环境变量和故障参数，装配依赖，打印或导出报告 | 默认只读取本地配置；真实模型凭据不写入 trace |
| `llm.py` | OpenAI 兼容接口、工具调用参数解析、离线 Mock 策略 | 模型看到消息历史和工具返回；Mock 是确定性策略 |
| `agent.py` | 维护对话、执行调用循环、校验 finish、构建报告和 trace | 不以模型自由文本决定保存事实 |
| `tools.py` | 素材、规则、授权、时段工具；保存前护栏和故障注入 | 拒绝不符合业务约束的写入，错误作为观察结果回传 |
| `store.py` | 加载合成数据、计算请求身份、保存本地 JSON 草稿 | 文件写入成功后才更新内存；未实现并发事务 |

一次模型响应可以包含多个工具调用，循环逐个执行，每个调用都计入步数。没有工具调用的响应也消耗一步，并提示模型通过工具继续。达到上限返回 `step_limit(N)` 与 incomplete，已经成功写入的草稿不会因达到上限自动回滚。

## 决策过程示例与证据入口

以 [冲突记录](../examples/llm/02_slot_conflict.log) 为例，M01 的处理过程为：

1. 读取素材，确认元数据齐全。
2. 执行渠道规则检查，观察到无风险。
3. 查询 18:00，观察到 X90 占用，并取得 19:00、20:00、16:00 三个替代候选。
4. 模型选择 19:00，保存为 pending_confirmation；执行器核对时段、占用和确认边界。
5. 存储返回 created 后，模型通过 finish 输出待确认事项。

对照 [占用解除后的记录](../examples/llm/05c_resubmit_after_slot_freed.log)，M01 回到原要求的 18:00，并成为 confirmed。多素材场景中的替代建议是 20:00，因为 19:00 是 M02 的原始诉求；不能把单素材和多素材场景的替代时间直接混为同一预期。

这些记录展示的是可检查的工具参数、观察摘要与下一步动作，不包含模型内部思维过程。工具返回的完整 JSON 被用于运行中的消息历史，导出 trace 主要保留返回摘要。

## 存储写入、重试与一致性

请求键由排序后的 `(material_id, channel, date, time)` 列表计算；条目内容哈希只包含素材 ID、渠道、日期、时段和状态，不包含模型自由生成的 note。这样，措辞变化不会引发无意义的版本更新。

写入过程是：生成候选新状态 → 写同目录临时文件 → 替换目标文件 → 更新内存。文件系统抛出 OSError 时，工具返回 storage_error，内存保持原状态；后续重试不能仅因内存里出现过该条目就返回 duplicate。故障注入的 storage_unavailable 则在真实写入前返回失败。

finish 使用 `_written_entries`，仅在存储返回 ok 时接受 scheduled / pending_confirmation。保存失败后，相关条目应为 unresolved，建议单独放在 unsaved_suggestion。此处同时约束单项结论和报告事实，防止顶层显示保存失败、单项却显示已排期的矛盾。

临时文件替换降低写入中途损坏目标文件的风险，但不提供数据库级事务、断电持久性或多进程隔离。不同请求生成的草稿之间也没有统一占用锁；冲突检查依据是加载的已有排期，以及当前草稿内部的时段。

## 明确的实现边界

- 当前 confirmations 只表达“素材 ID → 确认时段”，没有独立的风险审批记录和身份验证；演示中的商业合作风险停留在待确认状态，实际接入应拆分时段确认与商务风险审批。
- 模型自然语言 summary 保留为说明文字；自动判断应读取结构化字段。当前没有对任意 summary 文本做完整事实一致性校验。
- 步数限制约束调用数量，不等同于端到端超时或费用预算；模型接口自身有网络超时和重试，但最终网络异常尚未统一转换为结构化任务报告。
- 输入目前面向提供的合成请求，尚未提供完整 JSON Schema 校验；同一素材多条发布诉求、任意日期/渠道以及畸形参数需要额外验证。
- 替代工具只返回同日最近的三个候选。模型或 Mock 未选到可用候选，不等于已经遍历了全天所有时段，也不能据此证明全天无解。
